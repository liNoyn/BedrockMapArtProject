# 地図の陰影規則と BMAP の 3D 処理

BMAP が 3D マップアート（階段）で前提にしている規則と、それをどう検証しているかをまとめます。
統合版での確認状況は「4. Bedrock での確認状況」、実機での測定手順は [calibration.md](calibration.md) を参照してください。

## 0. Bedrock 1.26.51 で実測した規則（2026-10-18）

BMAP の陰影テストパッドを Bedrock 1.26.51 のワールドに置き、ゲームが描いた地図を読み取って測定しました
（測定点 8,032、候補モデルのうち「checker」が検証データで分類・RGB とも 100% 一致）。

| 北隣との高さの差 | x + z が偶数 | x + z が奇数 |
|---|---|---|
| +2 以上 | 明 | 明 |
| +1 | 通常 | **明** |
| 0 | 通常 | 通常 |
| −1 | **暗** | 通常 |
| −2 以下 | 暗 | 暗 |

- 倍率は 180 / 220 / 255 で、基本色 × 倍率 ÷ 255 を切り捨て（3 段階とも 100% 一致）。段差の大きさによる中間の明るさはありません。
- カーペット・ハーフブロックも同じ規則です。東西だけの段差は影響しません。
- Java 版の式 `d = Δy·4/5 + ((x+z)&1 − 0.5)·0.4`（`d > 0.6` で明、`d < −0.6` で暗）を **厳密に** 計算した結果と同じです
  （Java の倍精度計算では丸め誤差で偶奇の項が効かず、段差 1 でも常に明になります）。
- 「段差 2 が必要」という報告や、gd-codes・Nukkit が ±2 で建てるのは、±1 だと半分のピクセルしか変わらないためと説明できます。
- BMAP はこの規則を既定にしました。建築位置を地図の範囲に合わせると（既定）、ピクセルごとに許される段差の範囲
  （明: 奇数 +1 以上・偶数 +2 以上、暗: 偶数 −1 以下・奇数 −2 以下、通常: 0 と 奇数 −1・偶数 +1）から一番低い高さを選びます。
  常に 2 段で積むより建築が 27〜37% 低くなりました（テスト画像 6 枚、Valley・Floyd–Steinberg）。位置が分からないときは常に 2 段です。
- 「最大の高さ」を決めた場合は、実際の配置の高さを測りながら、上限いっぱいまで陰影を使えるように探します
  （例: 上限 12 で色差 1.40 → 1.33、上限なしでも 69 → 50 ブロック）。
## 1. 規則（Java 版）

縮尺 0 の地図の 1 ピクセルは、その列（x, z）で **一番上にあるブロック** の地図色を表示します。
色の明るさ（陰影）は、**真北（z − 1）の列の一番上のブロック** と高さを比べるだけで決まります。

| 北隣と比べた高さ | 陰影 | 倍率（Java 版の値） |
|---|---|---|
| 高い | 明 | 255 / 255 |
| 同じ | 通常 | 220 / 255 |
| 低い | 暗 | 180 / 255 |

- **差の大きさは関係ありません。** 1 段でも 10 段でも高ければ「明」です（Java 版）。
  そのため「暗」は何段でも一気に下げられ、Valley 階段はこれを使って低く抑えます。
- 統合版では「陰影を変えるのに 2 段の差が必要だった」という 2023 年のユーザー報告（現行版では未確認）もあるため、BMAP は **陰影が変わる最小の段差（step）を
  色プロファイルの設定** にしています（既定 1）。step を 2 にすると、±1 の差は「通常」として扱い、階段は 2 段ずつ作ります。
  地図シミュレーター・減色（高さの上限は段差の数 = 上限 ÷ step）・建築配置・3D ビューのすべてがこの値に従います。
- **東西の隣は関係ありません。** 列（x）ごとに完全に独立しています。
- 地図の 1 行目は、地図の範囲のすぐ北の行（支え行）と比べます。BMAP は必ず支え行（z = 0）を出力します。
- 北隣の列が空（透明ピクセル）の場合、そこに見えるのは建築の下の地形です。陰影は地形の高さで決まり、予測できません。
- 支えブロックがその列の見えるブロックより上に出ると、それが「一番上」になって地図の色が変わります。
- 砂・砂利・コンクリートパウダーは下が空だと落下し、カーペット・感圧板は壊れます。どちらも地図が変わります。
- 135 / 255 の 4 段目の明るさは建築では出せません（地図データを直接書いた場合だけ）。

## 2. BMAP での扱い

### 地図シミュレーター（`Shading/MapShading.cs`）

ブロックの配置（見えるブロック・支え行・支えブロックすべて）**だけ** から、上の規則で地図を描き直します。
減色の段階で計画した色とは独立に計算するので、両者を比べると「減色 → 高さ → 支えブロック」の流れ全体を検証できます。

`ShadingAnalyzer` は次を報告します。

- 計画した色と違うピクセル（**常に 0 であるべき**。テストで全方式・全支えモードを確認）
- 北隣が空で地形しだいのピクセル
- 落下・破損するブロック
- 暗・通常・明のピクセル数、最も高い列、平均の高さ、段差と 2 段以上の落差の数、列ごとの高さ分布

### 見つかった不具合

シミュレーターで、Valley 階段と「すべて（サバイバル向け・最適化）」の組み合わせで
**支えブロックが隣の低い列の見えるブロックより上に置かれ、地図に写ってしまう** 問題が見つかりました
（128×128 の例で 13〜40 ピクセル）。支えブロックは必ずその列の見えるブロックより下に置くよう修正し、
回帰テストを追加しています。

### 高さの上限

上限を決めた場合、列ごとの必要な高さは「明（または暗）の連続の長さ」で決まります（通常は連続を切らず、
逆の陰影で切れます）。BMAP はこの連続の長さを状態にした動的計画法（Viterbi）で、上限内で色差が最小になる陰影を
列ごとに求めます（ディザなし・規則ディザでは最適解）。

- Classic 階段は常に 1 段ずつ上下する（一気に下げない）ため、高さは全段差の累計になり、連続の長さでは抑えられません。上限は Valley 専用です。
- 誤差拡散ディザでは、連続が上限に達したところで止め、その色の誤差を周囲に拡散します。
  「先に Viterbi で陰影を計画し、その中でディザし直す」方式も試しましたが、
  見た目の色差は全ての上限で悪化しました（例: 上限 4 で ΔE 3.44 → 3.59）。そのため採用していません。

### 3D ビュー（`Preview/Viewer3D.cs`）

- 面ごとの陰影は地図シミュレーターと同じ規則で計算します（「地図に写る色」表示を真上から見ると予測地図と一致することをテストで確認）。
- 「陰影」表示: 暗 = 青、通常 = 灰、明 = 黄。予定と違う色は赤、地形しだいは紫、落下・破損は橙。
- アンビエントオクルージョン（Minecraft のスムースライティングと同じ 4 隅の判定）と、太陽方向への影。
- チャンク（16）と地図（128）の境界線、表示する高さの上限（1 段ずつ建てるとき用）、最も高い列への移動。
- 遠近法では透視補正したテクスチャ座標で描画します。

## 3. 確認方法（陰影テストパッド）

実機で規則を測る手順は [calibration.md](calibration.md) にまとめました。ゲームに地図を描かせ、その地図をワールドの
データベースの一時コピーから **読み取るだけ** で、段差 −4〜+4 ごとの明るさ・陰影が変わる最小の段差・倍率を求めます。

## 4. Bedrock での確認状況

| 項目 | 状況 | 根拠 |
|---|---|---|
| 陰影の倍率 180 / 220 / 255 | **確認済み** | Bedrock 1.21.132〜1.26.51 が描いた地図 12 枚（約 19 万ピクセル）で、基本色 × 180/255・220/255・255/255（整数の切り捨て）と完全に一致するピクセルを、クォーツ・白・石・橙・赤・オークなどの色セットで 3 段階すべて確認 |
| 一部の色セットの基本色 | **確認済み**（13 色セット） | 同上。2 段階以上で各 3 ピクセル以上見つかった色セットだけを確認済みとしています（`palettes/` の `status`） |
| 135 / 255 | 建築では出ない | 上の地図では 1 ピクセルも見つかりませんでした |
| 何もない列 | 黒（#000000・不透明）で描かれるようです | 上の地図に約 8.7 万ピクセル（何が描かれた結果かは未確認）。Java 版の透明とは異なります |
| 水 | 対象外 | #1E5AF5 などバイオームの水の色に近い値で、Java の水の地図色とは一致しません |
| 陰影が変わる段差 | **確認済み**（1.26.51） | ±1 は座標の偶奇で交互、±2 以上は常に（「0. Bedrock 1.26.51 で実測した規則」） |
| 丸め方 | **基本色 × 倍率 ÷ 255 の切り捨て** | 明・暗 3,577 ピクセルで、この方式だけが説明できるものが 112、gd-codes の方式だけのものは 0 |
| ブロックと色セットの対応 | 未確認 | 色の値は確認できても、どのブロックがその色になるかは色テストパッドで確認します |
