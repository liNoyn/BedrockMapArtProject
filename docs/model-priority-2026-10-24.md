# モデル別の配色評価と精度強化（第4段階）

強い色数制限で輪郭と平均色を両立できない場合は、ユーザー指定の方針を適用する。
イラスト（Optimized）・バランス（Hybrid）は輪郭、ブレンド（Perceptual）は平均色を優先する。
既存プロジェクト・CLI用に残している他の方式も平均色の評価を維持する。

## 配色候補と判定

第3段階の選択中の色距離による計画に加え、CIEDE2000で計画した候補も実際に変換する。
変換自体はユーザーが選んだ色距離・モデル・高さ条件で行う。
従来の使用頻度による削減も残し、同じ配色は再変換しない。

最初に平均色の多尺度評価で従来の最良候補を決める。輪郭優先の2方式では、
その候補から輪郭の重みを含む評価へ進み、通常の配色候補も再評価する。
さらに輪郭の重みを使って計画した候補を比較する。
選択中の色距離とCIEDE2000の両方が悪化せず、少なくとも片方が改善する場合だけ切り替える。
この判定は同じ高さ計画条件の比較であり、高さ探索全体の大域最適性を保証するものではない。

高さ制限付きの実際の建築では、支持ブロックと配置グリッド、同色ブロックの振り分けまで
反映した配置が高さ内に収まる候補を先に優先する。同じ可否の候補同士に上記の画質判定を適用する。
高さを超える候補に切り替えてから陰影数を減らすと、元々収まっていた候補より画質が落ちるためである。
48pxの輪郭画像・6色・高さ4のBayer4/Bayer8では、変更前の高さ3・平均誤差5.377/5.362から、
高さ4・5.055/5.036を得る回帰テストを追加した。

また、探索中に得た高さ内の結果を保持する。より多い段差を許すと配色が変わり、
かえって画質が落ちる場合があるため、最後にこれらを用途別CIEDE2000の総合値で比較する。
ここでは色距離の異なる指標を混ぜず、輪郭優先・平均色優先の目的に合わせて選ぶ。
2色・高さ4の細線画像では、Ordered3が探索途中に得ていた平均誤差0.714の結果を、
最後の許容段差で得た1.538の結果に上書きしないことを回帰テストにした。
まだ試していない全ての段差数・配色を総当たりする処理ではない。

## 輪郭の重み

元画像のOklabで各画素と周囲8画素の最大色差を求める。
対称な微分だけでは1ピクセル線の中心が消えるため、近傍との差を直接使う。
明るさに加えて色相・彩度の境界も対象とし、透明画素とその隠れたRGBは除外する。

- 色差0.015以下には追加の重みを与えず、0.015〜0.15で強さを0〜1に増やす。
- 重みは `1 + strength × maxStrength × visibleCount / sumStrength`。
  強い輪郭がある場合、画素平均と輪郭への追加重みを同じ総量にする。
  解像度の増加で細線の割合が減っても無視されにくくする。
  弱い変動しかない場合は追加の総量も小さくなる。
- 同じ重みを配色計画と実際の多尺度評価に使う。ぼかしは従来の線形光の処理を維持する。

あらゆる線を必ず保存する規則ではない。イラスト・バランスでは、細線を残す代わりに
通常の画素平均誤差が増える場合がある。`QualityScore.Measure` は通常の平均値を維持し、
`MeasureForModel` で用途別の値を測る。色数制限のない変換には今回の配色探索を追加しない。

## 計算の改善

配色と色距離から決まる置換コストだけを最大8パレットまで共有する。
パレットの並び・実際のRGB・陰影・色距離をキーに含め、画像の分布や輪郭の重みは共有しない。
256項目を超えるパレットは共有キャッシュに残さない。
計算完了した行だけを公開し、キャンセルされた途中の計算を再利用しない。
色の変更・並べ替え・並列実行・キャンセル後の再実行をテストする。

Optimizedの混色計画から、利用前に上書きされていた候補のソートも除いた。
128×128・42条件・各5回の測定では、Optimizedの平均中央値が59.34→55.38msとなり、
原画像を含む49枚のPNGハッシュは一致した。この改善率は今回の測定環境での値であり、
追加の配色探索には別途時間が必要になる。

## 検証の再現

### 48pxの比較

6画像（勾配・混在・イラスト・輪郭・coffee・細線）、FlatとValley/高さ4、全17方式を
2色・6色制限で比較した。各204条件、計408条件。直前の平均色評価版との比較である。
用途別の誤差はCIEDE2000の多尺度総合値で、小さいほど良い。
輪郭の重みがモデル間で異なるので、モデル間の順位ではなく同じモデルの前後比較に使う。

|制限|モデル|用途別誤差 変更前→後|通常の平均誤差 変更前→後|処理時間の平均中央値 ms 変更前→後|
|---|---|---:|---:|---:|
|2色|イラスト|11.280→10.272|10.170→10.412|76.25→123.89|
|2色|バランス|11.260→10.122|9.945→10.217|75.32→118.93|
|2色|ブレンド|9.889→9.889|9.889→9.889|63.09→63.90|
|6色|イラスト|5.813→5.619|5.800→5.801|78.28→128.70|
|6色|バランス|5.660→5.493|5.577→5.500|76.71→125.56|
|6色|ブレンド|5.359→5.359|5.359→5.359|66.50→68.76|

各条件3回の中央値を画像・地形条件で平均した。速度の保証値ではない。
色数制限時のイラスト・バランスは追加の候補変換と評価で時間が増える。
2色では輪郭保存の代わりに通常の平均誤差が約2〜3%増えることも、意図した方針の結果として示す。
408条件の用途別誤差に悪化はなく、Bayer4/Bayer8の高さとの干渉による悪化も解消した。

### 256pxの比較

同じ6画像・2地形条件・主要3方式・6色制限の36条件でも用途別誤差の悪化はなかった。

|モデル|用途別誤差 変更前→後|通常の平均誤差 変更前→後|処理時間の平均中央値 ms 変更前→後|
|---|---:|---:|---:|
|イラスト|6.545→5.706|6.131→6.311|1600→2970|
|バランス|5.718→5.308|5.828→5.727|2012→3533|
|ブレンド|5.527→5.527|5.527→5.527|1925→2068|

今回の色数制限付きの比較では、イラスト・バランスは約1.6〜1.9倍の処理時間になった。
通常の色数無制限の変換に、この追加探索の時間がかかるわけではない。
輪郭優先のイラストでは通常の平均誤差が約3%増え、用途別誤差は約13%減った。
測定環境はWindows、.NET 8.0.32、論理CPU数12。各条件3回の中央値を平均した値である。

### 最終確認

- Releaseビルド：警告0・エラー0。
- 自動テスト：555件成功（Core 546件、GUI 9件）。
- 配色制限の比較：444条件で用途別誤差の悪化0、色数超過・不透明配置の不整合0。
- 高さ検証：全17方式×5画像×高さ2/4/8/16×配置グリッド有無×支持2方式の1360条件、失敗0。
- 色数無制限：原画像を含む828枚のPNGが直前版とSHA256一致。
- `git diff --check`：問題なし。

成果物の `Verify.ps1` で、条件数・配色制限・物理配置・TRX・PNGを再確認し、
`summary.json`、`quality-summary.json`、`comparison.json` を生成する。
`final-source/` にCore・パレット・比較ツール・配色制限のテスト用ソースを保存し、
`source-sha256.json` にそのハッシュを記録する。
`model-priority-comparison.png` は2色制限の細線の比較で、左から原画像・変更前・変更後。

これらは対象画像と条件内の検証であり、全画像・全配色の大域最適性を証明するものではない。

証拠は `artifacts/codex-reviews/2026-10-24-model-priority/` に保存する。
基準は直前の平均色評価版 `2026-10-24-palette-candidates/final-source/`。
第3段階との比較結果も同ディレクトリ群に残す。

保存済みPNGを同じモデル別評価で採点し直すには次を実行する。

```powershell
dotnet run --project tools/DitherBench -c Release -- compare-policy before-dir after-dir comparison.json
```

条件と原画像が一致しなければエラーにする。平均色と用途別の誤差、記録済み処理時間、
画素の一致を別々に出力する。通常のDitherBenchの `Overall` は引き続き平均色の値であり、
新しい評価値と古い平均値を直接比較しない。
