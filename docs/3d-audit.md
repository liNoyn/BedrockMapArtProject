**3D技術の総点検・修正記録 — 2026-10-24**

対象: ローカルの BedrockMapArtGenerator。調査開始時の HEAD は `965cb43`（v0.15.2）。
高さ生成、支え、陰影シミュレーション、メッシュ、投影、テクスチャ、操作・非同期描画、2D/高さ図、構造物出力を通して調査した。
今回の変更はローカルの作業ツリーにあり、コミット・公開はしていない。

結論: Bedrock向けの高さ生成と、描画専用の3Dエンジンを分ける現在の構成は維持できる。
ただし、透視投影の深度、カメラの収まり、プレビュー間の陰影、描画更新と選択情報の対応などには修正が必要だった。
以下を実装し、既存191件に回帰テスト19件を追加した。Release構成の全210テストが合格している。

| 調査対象 | 判明した問題・判断 | 今回の対応 |
|---|---|---|
| 透視投影と深度 | UVは遠近補正されるが、カメラ空間の深度は画面上で単純に線形補間していた | 深度にも逆距離による補正を適用。独立した光線と立方体の交差計算で選択結果を照合 |
| 三角形の境界 | 内外判定の許容幅が大きく、面の外にある画素までブロックとして選択される場合があった | 許容幅を縮小し、光線との照合テストで検証 |
| カメラ距離 | 水平サイズだけから距離を決め、高く細い構造物では頂点がカメラの後ろに入り得た | 高さを含む包囲球から距離を決定。通常のオービット操作で構造物全体が前方にあるようにした |
| 全体表示 | 推定式と最小ズーム0.25のため、高い建築・細長い画面・大きい領域が収まらない | 包囲箱8頂点を実際の投影式で評価。上下限の中央と画面寸法からズームとパンを決定 |
| 透視投影のパン | パン量に頂点ごとの遠近倍率が掛かり、操作量と見え方が深さによって変化した | 投影後の画面平行移動に統一。最高地点への移動も同じ式で計算 |
| 底面 | 5方向の面しかなく、透視投影の低い視点から浮いたブロックの下面が欠ける | 必要な底面を追加。許可されるカメラ位置から絶対に見えない底面は生成しない |
| 2Dの陰影 | 単純な高低差の符号を使い、Bedrockの偶奇規則やしきい値と一致しない | 地図シミュレーターの結果を使用。テクスチャのない配置図で一致を検証 |
| 3Dの地図色 | メッシュ側の別計算に依存し、段階的陰影や別プロファイルの色を正しく反映できない | 完成した全体配置から北隣との差を保持し、描画時のプロファイルの規則で分類・着色 |
| テクスチャ | 在庫用アイコンを全方向の面に使用。薄いブロック用のアイコンマスクも3Dに混入 | 上・北・南・西・東・下の画像を解決し、在庫アイコンと別キャッシュにした。取得処理も各面を対象に変更 |
| 高さの提案 | Classic選択時、実際には制限を適用できないClassicを「上限付き候補」として表示 | 制限付き候補はValleyにし、Classicの無制限結果を比較用に維持 |
| マウス選択 | 旧画像のブロックIDを新メッシュへ照会でき、別ブロックを示す可能性があった | 画像・IDバッファ・メッシュ・陰影レポートを対応付けて保持 |
| 非同期描画 | 古い設定の描画が、操作後に完成して表示される | 世代番号を照合して古い結果の公開を抑止。ビューを閉じた後の公開も抑止 |
| 操作・リソース | キャプチャ喪失後のドラッグ状態、領域外のホバー、古いBitmapの保持 | 操作終了・ホバー消去処理を追加。置換されたBitmapを破棄 |
| 表示の補助操作 | 選択中の地図範囲に関係なく全体の最高地点へ移動していた | 現在のメッシュに含まれる最高地点へ移動 |
| 半解像度描画 | 片方の寸法が64付近で、半解像度にならず縦横比が崩れる | 両寸法を半分にし、実際の幅比率でズームを調整 |
| 検証結果の表示 | 北隣が空で地形依存の画素があっても `IsExact` がtrueになり得た | 地形依存がある場合も完全一致扱いから除外 |
| 構造物の縦分割 | 分割高さ0/負値で無限ループの恐れ。極端に大きい値では加算がオーバーフロー | 不正値を拒否し、分割開始位置の計算を64bit化 |

高さ上限の意味は既存仕様を維持した。`MaxHeight` はブロックの段差範囲であり、最低Y=0の場合に占有するブロック層数は `MaxHeight + 1`。
高さの探索は実際の支えを生成した配置で判定する。Classic自体にValleyの制約を流用する変更はしていない。

**参考元との比較**

[MapartCraftの3D実装](https://github.com/rebane2001/mapartcraft/blob/master/src/components/mapart/viewOnline3D/viewOnline3D.js)は、
Three.js / WebGL、16×16×16のチャンク、隣接ブロックとの境界面の省略、テクスチャアトラス、光線による選択を使う。
こちらはC#のソフトウェアラスタライザーで、列単位の疎な占有インデックスとIDバッファを使う。
チャンク化と境界面の省略は参考になるが、描画APIとデータ構造をそのまま移す必要はない。参考コードの転記は行っていない。

地図の陰影を決める規則と、3D表示を見やすくする照明・AO・影は別のもの。
既存のBedrock実測に基づく偶奇モデルは維持し、Java向けの高さ規則への置換は行っていない。
地図色を比較するときは3Dの照明・輪郭・グリッド・ハイライトを無効にして、上面の画素を評価する。

**検証結果**

- 変更前: 全191テスト合格。描画については「画像が生成される」だけでなく幾何学的に照合するテストが必要だった。
- 変更後: `dotnet test BMAP.sln -c Release --no-restore -p:BundleTextures=false --verbosity quiet` で全210件合格。
- Releaseビルド: 警告0、エラー0。`BundleTextures=false` を使い、ビルド中の外部画像取得を無効化した。
- 新規テスト: 正射影・透視投影5条件で、画素中心からの光線と全立方体の交差距離を計算し、描画IDと比較。
- 高く細い構造物（Y=0/90/180/380）を、横長600×120と縦長120×600の画面で評価し、全頂点の収まりとカメラ前方への配置を確認。
- Checker / Threshold / Graded の3モデルで、照明を切った3D上面・テクスチャなし2D・地図シミュレーターを画素単位で比較。
- 切り出し領域の外に北隣がある場合、面別画像の解決・描画、在庫アイコンとのマスク分離、高さ提案、縦分割の不正値・極大値を検証。
- 128×128の生成サンプル: 支えを含む最大Y=12、色の不一致0、地形依存0、落下0、脱落0。
- 同サンプルを縦8ブロックで分割: Tiles64は11ピース、PerMapとWholeは各2ピース。全方式で配置の欠落・重複0。

Windows GUIの実際のドラッグ操作と、新しい出力のMinecraft実機読み込みは今回実施していない。
既存資料に記された過去の実機測定と、今回実行したシミュレーター・ファイル検証は区別する必要がある。

**描画負荷の測定**

Windows 10.0.26200 / .NET 8.0.32 / 論理プロセッサ12、Release構成。
高さを `(z / 8 + x / 16) % 16` とした石の合成配置を使い、1200×800、透視投影、照明と輪郭あり、テクスチャなしで測定した。
描画は1回ウォームアップ後の3回の中央値。メッシュ時間は1回の測定値で、初回JITやスレッド初期化の影響を含む。
一般画像や全ブロック種類の性能保証、および変更前後の速度比較ではない。

| 地図枚数 | 配置ブロック | 面数 | メッシュ生成 | 描画中央値 |
|---|---:|---:|---:|---:|
| 1×1 | 16,512 | 22,928 | 38ms | 35ms |
| 2×2 | 65,792 | 90,912 | 26ms | 28ms |
| 4×4 | 262,656 | 362,048 | 119ms | 72ms |
| 8×8 | 1,049,600 | 1,444,992 | 239ms | 222ms |

この条件の8×8では描画だけで約4.5fps相当。通常の地図単位表示は扱えるが、大型全体表示を滑らかにするには追加対策が要る。
既存の疎なColumnIndexと境界面の省略は有効なので維持する。

**残る技術的な制約と次の優先順位**

1. 大型表示: チャンクの包囲箱による可視判定と変更チャンクのみの再生成を優先する。現在も描画ごとに全メッシュの面を走査する。
   操作中のキャンセルにも未対応で、古い結果の表示は防げるが、その計算時間は消費する。GPU化はこのCPU負荷を測定しながら別途判断する。
2. ブロック形状: メッシュと選択は1ブロック立方体の近似。ハーフブロック、階段、カーペット、トラップドアなどの実形状、
   block statesによる面方向・UV回転は未対応。面別テクスチャ対応は形状対応を意味しない。
3. 透明表現: ガラス・葉の透明画素を不透明な代替色で埋める実装を維持。アルファテストや半透明合成は未対応。
   透過対応には、透明ブロック間の面省略と深度・選択の扱いも併せて設計する必要がある。
4. 照明: AOは占有グリッド、日影は列の最高高さと半ブロック刻みの近似。浮いたブロックの下の空間や細かな形状の正確な影は再現しない。
   3D照明の見た目からゲームの地図色を推定しないこと。
5. 静的な等角図: `RenderIsometric` は描画順を並べる従来方式で、独立した深度バッファを持たない。
   相互に遮蔽する複雑な配置の正確さが必要な用途では、今回検証した `Viewer3D` へ統合するのがよい。
6. 高さ探索: HeightPlannerの二分探索は量子化パラメーターと実高さの傾向を利用する。
   実配置での上限確認は行うが、全画像で色誤差が最小、または空き高さを最大限使うことの証明にはなっていない。
7. 実機: 特殊形状・バイオーム・他バージョンを含む検証は既存の課題として残る。今回の修正の実機保証を追加したものではない。
